# Interfaces

What Apiary-Keeper exposes and what it depends on: the contract each side may rely on. The interface letters and the
section numbers (D.1, F.3, …) are the ones the code's comments cite. Requirement IDs (`UC-n`, `FR-n`, `NFR-n`) are
defined in [`REQUIREMENTS.md`](REQUIREMENTS.md), design decisions (`D-n`) in [`ARCHITECTURE.md`](ARCHITECTURE.md),
and every setting named here in [`DEPLOYMENT.md`](DEPLOYMENT.md) §3.

Built today: the server's own HTTP surface (Interface D, D.1), the media bucket (Interface F) and the server's side of
Keycloak (Interface L), against the local and test realm only — no deployed environment runs Keycloak yet. The rest
are planned and listed so their letters keep their meaning.

## Interface D — the server's HTTP surface

Two surfaces on one host (FR-42), of which the first is built:

- **The internal API**, for the family app (and later the Telegram webhook). Every yard, colony, inspection, media and
  invitation request needs a signed-in user whose role and `account_id` it checks: from the cookie session of the
  sign-in backend in the API for a browser, or from a Keycloak-issued bearer token for an automated client (Interface
  L). Sign-in is a setting (`SignIn__Authority`); where it is off, those requests answer `503`. Until sign-in is on
  in a deployed environment, a deployment strangers can reach sits behind the proxy's shared-password gate, which
  covers every path but `/health`.
- **The public API** (Phase 2), for the customer website: read-only catalog, order and form endpoints, rate-limited,
  accepting requests only from the site's domain; the seller is resolved from the site's domain (FR-43).

An optional module's endpoints answer `404` while its feature flag is off (FR-57).

### D.1 HTTP endpoints and OpenAPI

The OpenAPI document is generated by the server (`AddOpenApi()`, titled "Apiary-Keeper API", published in
Development); this section is the contract, that document is the exact shape. Besides the endpoints below the server
answers:

- `GET /health` — `200` with the running version, `{"version":"X.Y.Z"}`, once it is serving; anonymous.
- `/metrics` — Prometheus metrics, for scraping on the private network; the proxy refuses it from outside.
- The family app's files from `wwwroot`: `index.html` at `/`, `/manifest.webmanifest`, `/sw.js`, the icons and
  assets. **Any other path is `404`.** The app's screens live in the URL fragment (`/#/yards/{id}`), which the browser
  never sends, so the server only ever sees `/` (D-20). Once the app's service worker is installed, a navigation to an
  unknown path on that device gets the cached app shell instead.

The API lives under `/api`, which the service worker never answers for.

#### Sign-in endpoints

UC-18, NFR-6, D-19. They exist only where `SignIn__Authority` is set, and are `404` everywhere else.

| Method | Path | Operation | Success | Failures |
|---|---|---|---|---|
| GET | `/api/auth/login?returnUrl=` | `SignIn` — start the browser's sign-in | `302` to Keycloak: the authorization code flow with PKCE `S256` as the confidential client, the request pushed to Keycloak first (RFC 9126) when it offers that. `returnUrl` is kept only when it is a path on this host (a screen in the fragment, `/#/yards/7`, included), otherwise `/` | — |
| GET | `/api/auth/callback` | (the OpenID Connect handler's) — Keycloak returns the code here | `302` to the return URL, setting the session cookie | `403` `NotAllowed` when the sign-in did not complete (a refused or replayed callback, a token without a subject or a single `account_id`) |
| POST | `/api/auth/logout` | `SignOut` — end the browser's session | `200`, `{"endSessionUrl": …}`: the session is gone from the server, its cookie cleared, and Keycloak's own session ended over the back channel; the URL is Keycloak's sign-out page for this client, which the browser may still visit to clear Keycloak's cookies (Keycloak asks to confirm); null when Keycloak could not be reached | `403` with the session cookie and no `X-CSRF: 1`; `405` for any other method |
| GET | `/api/auth/me` | `GetSignedInUser` — the caller's principal | `200`, `{"sub": …, "accountId": …, "roles": [ … ]}` — the same for the session cookie and a bearer token | `401` when not signed in (never a redirect) |

- **The session cookie** (`__Host-apiary-keeper-session`; `apiary-keeper-session` where `SignIn__RequireHttps` is
  off, for a local http Keycloak) carries only a protected session id: `HttpOnly`, `SameSite=Lax`, path `/`, `Secure`
  with https required. The session — the principal's `sub`, `account_id` and roles, and beside it Keycloak's refresh
  token, never sent to the browser — is on the server, in memory. It ends after `SignIn__SessionIdleTimeout` without a
  request, at `SignIn__SessionMaxLifetime` however active, and with the server's restart.
- **The renewal.** On a request with the session cookie whose access token is within 30 seconds of expiring, the
  server presents the session's refresh token to Keycloak and rebuilds the principal from the new ID token, so a role
  or `account_id` change made in Keycloak reaches the session then, and not before (about every 5 minutes). A refresh
  Keycloak refuses — the user disabled, the refresh token revoked, spent or expired, the Keycloak session ended — ends
  the session: `401`, the cookie cleared, sign in again. While Keycloak cannot be reached the session is kept, but a
  request past the access token's expiry is `401` until it answers.
- **A bearer token** (`Authorization: Bearer …`) is decided by the token alone, whatever cookie comes with it:
  Keycloak's RS256 signature, the issuer `SignIn__Authority`, the audience `SignIn__Audience` (`apiary-keeper-api`),
  its lifetime, and that it is an access token (an ID token is refused whatever its audience); otherwise `401` with
  `WWW-Authenticate`. It starts no session. Both paths give the same principal.
- **The CSRF check.** Any request that is not a `GET`, `HEAD`, `OPTIONS` or `TRACE` and carries the session cookie must
  carry the header `X-CSRF: 1` exactly, or it is refused before its endpoint with `403`, a `NotAllowed:` problem. A
  request without the cookie — a bearer call, or an anonymous one — is not checked. The family app sends the header on
  every write; the media upload to the bucket is not a call to the API and carries only the headers its URL names
  (F.3).

#### Who may call the apiary endpoints

UC-18, NFR-6, NFR-8, D-19, D-22. Every yard, colony, inspection and media endpoint below is authorized from the
principal alone, by either path:

- **Signed in, as an `owner` or a `helper`** — the field work of UC-1, UC-3 and UC-9. No credential, or one that
  fails, is `401` (never a redirect); a `grower`, a `customer` or a user with no role is `403` — before anything is
  read.
- **The account is the token's `account_id`**: every query is filtered to it (NFR-8); a request never names its
  account.
- **The acting user is the user of that account whose `ExternalSubject` is the token's `sub`** — the user every written
  row is stamped with, set when the user is invited (*Invitation endpoint*, below), never the email. A token whose
  account has no `Accounts` row is `403` `NotAllowed:` *your account is not set up on this server*; a `sub` no user of
  the account holds — another account's user included — `403` `NotAllowed:` *you are not a user of this account*;
  nothing is read or written. A found user is trusted for 30 seconds and a refusal is never remembered, so a user set
  up later is served on the next request.
- **Where sign-in is off** no caller has an account, so every apiary endpoint answers `503` `Unavailable:` *no
  signed-in account: sign-in is not set up on this server* and nothing is read or written.
- A browser keeps its role and account until its session's next renewal; a bearer caller, until its access token
  expires.

#### Invitation endpoint

UC-18, FR-74, NFR-6, D-22. An account's owner invites a helper or grower by email; Keycloak creates the user in the
owner's account and emails the invitation, through the server's service account (Interface L).

| Method | Path | Operation | Success | Failures |
|---|---|---|---|---|
| POST | `/api/invitations` | `InviteUser` — invite someone to the account | 201, `{"userId":…,"email":…,"name":…,"role":…}`, no `Location` | 400, 401, 403, 409, 503 |

- **Who:** a signed-in `owner` only, acting in its own account as its own user (*Who may call the apiary endpoints*,
  above, with `owner` alone): any other role is `403` before anything is looked up.
- **The request:** `email`, one address of at most 254 characters, lower-cased (it is also the user's sign-in name);
  `name`, the name shown beside the user's rows, at most 200 characters; `role`, `helper` or `grower` — `owner` is
  refused (*created by the Keycloak administrator*) and so is `customer` (*the storefront's*, FR-38). Each failure is a
  `400` keyed by its field, and Keycloak is not asked.
- **What happens:** Keycloak creates the user with the owner's `account_id` and the one role and emails its
  invitation, a link to verify the address and set a password, valid for `KeycloakAdmin__InvitationLifetime`. Then the
  server writes the user's `Users` row in the owner's account with **`ExternalSubject` the Keycloak user id**, which is
  the `sub` the user's tokens carry, so the user acts as that row from its first sign-in. A row that cannot be written
  removes the Keycloak user again, and the call is a `500`; the invitation email has already gone by then, so its link
  fails at Keycloak and the owner invites again.
- **Failures:** an address Keycloak already has is `409` `Conflict:` and nothing is created; Keycloak failing or
  unreachable is `503` `Unavailable:` and nothing is left behind; with the service account unset
  (`KeycloakAdmin__ClientId`) it is `503` *invitations are not set up on this server*; with sign-in off, `503` as every
  account endpoint.
- **Not here:** re-sending or withdrawing an invitation, and any change to an existing user; a customer account
  (FR-38, Phase 2).

#### Paging

Every list takes `limit` (1–100, default 50) and `cursor`, and answers `{"items":[…],"nextCursor":…}`. `nextCursor`
is opaque: pass it back as `cursor` for the next page; it is `null` on the last page.

#### Errors

Failures are RFC 9457 problem details (`application/problem+json`) whose `title` starts with the category, and whose
status the category fixes:

| Status | Title starts | When |
|---|---|---|
| `400` | `Validation:` | A field is invalid or breaks a rule; `errors` has an entry per field, keyed by its JSON path (`landowner.terms`, `findings.queenSeen`) |
| `401` | — | Not signed in, or the credential failed; no body for a session, `WWW-Authenticate` for a bearer |
| `403` | `NotAllowed:` | The caller's role may not call the endpoint, its account or user is not set up (*Who may call the apiary endpoints*), or a write with the session cookie lacks `X-CSRF: 1` |
| `404` | `NotFound:` | The record does not exist **or belongs to another account** — another account's record is never acknowledged |
| `409` | `Conflict:` | An invitation for an address Keycloak already has |
| `503` | `Unavailable:` | Sign-in is off (no account), the bucket or the invitation service is not configured, a dependency did not answer, or a colony changed while the change was being recorded. Checked before anything is read or written; retry later |
| `500` | — | An unexpected failure: a bare problem with no detail |

A malformed body, an unknown route or a method an endpoint does not take are the framework's own `400`, `404` and
`405`.

#### Warnings

A change that is valid but may be a mistake only the caller can judge is recorded as given, and its result carries
`warnings`: an object keyed by request field like a validation problem's `errors`, each message starting `Warning:`.
It is absent when there is nothing to say and on every read, and it is never stored. Today the only warning is on a
requeen dated before the current queen's introduction:

```json
"warnings": {"introducedOn": ["Warning: introducedOn 2026-03-01 is before 2026-05-10, the day the queen she replaces was introduced. It was recorded as given; recorded events are never changed."]}
```

The family app shows a warning as a dismissible notice, never as a failure.

#### Yard endpoints

UC-9, FR-1, FR-2. Every request acts for the signed-in caller's account, as the user its token names.

| Method | Path | Operation | Success | Failures |
|---|---|---|---|---|
| POST | `/api/yards` | `CreateYard` — record a yard and its landowner | 201, the yard, `Location: /api/yards/{id}` | 400, 401, 403, 503 |
| GET | `/api/yards?limit=&cursor=` | `ListYards` — the account's yards by name | 200, a page | 400, 401, 403, 503 |
| GET | `/api/yards/{id}` | `GetYard` — one yard | 200, the yard | 401, 403, 404, 503 |
| PUT | `/api/yards/{id}` | `UpdateYard` — replace every field of a yard | 200, the yard | 400, 401, 403, 404, 503 |

- **A yard** is `name` (required, ≤ 200), `location` `{latitude, longitude}` (required; decimal degrees, −90 to 90
  and −180 to 180), `state` (required; `TX` only for now), `county` (required, ≤ 100), `accessNotes` and
  `forageNotes` (optional, ≤ 2000 each), and `landowner`: `contact` (required, ≤ 500), `terms` (required; `honey`,
  `fee` or `free`), `nearbyCrops` (optional, ≤ 1000) and `sprayContact` (optional, ≤ 500).
- Text is trimmed and blank optional text is stored as null; `state` and `terms` are matched without regard to case.
  A result adds `id` and never carries the account. Yards are not deleted through the API.

#### Colony endpoints

UC-3, FR-4, FR-5, FR-6. The same signed-in account and acting user. A colony's history is **append-only** (D-2):
every change below appends a lineage event and returns the colony's state projected from it. No endpoint updates or
deletes an event: `PUT`, `PATCH` and `DELETE` are answered `405` (or `404` for a path naming one event) before
anything is read.

| Method | Path | Operation | Success | Failures |
|---|---|---|---|---|
| POST | `/api/colonies` | `RegisterColony` — an existing colony, and its queen when known | 201, the colony, `Location: /api/colonies/{id}` | 400, 401, 403, 503 |
| POST | `/api/colonies/swarm-captures` | `CaptureSwarm` — a captured swarm as a new colony | 201, the colony, `Location` | 400, 401, 403, 503 |
| GET | `/api/colonies?limit=&cursor=` | `ListColonies` — the account's colonies by tag id, with their current queens | 200, a page | 400, 401, 403, 503 |
| GET | `/api/colonies/{id}` | `GetColony` — one colony's current state and queen | 200, the colony | 401, 403, 404, 503 |
| GET | `/api/colonies/{id}/events?limit=&cursor=` | `ListColonyEvents` — its lineage, oldest first | 200, a page of events | 400, 401, 403, 404, 503 |
| GET | `/api/colonies/{id}/queens?limit=&cursor=` | `ListQueens` — its queens, newest introduction first | 200, a page of queens | 400, 401, 403, 404, 503 |
| POST | `/api/colonies/{id}/splits` | `SplitColony` — a new colony split from this one | 201, the new colony, `Location` | 400, 401, 403, 404, 503 |
| POST | `/api/colonies/{id}/merges` | `MergeColony` — merge this colony into another | 200, this colony, now `merged` | 400, 401, 403, 404, 503 |
| POST | `/api/colonies/{id}/requeens` | `RequeenColony` — introduce a new queen | 200, the colony with its new queen | 400, 401, 403, 404, 503 |
| POST | `/api/colonies/{id}/moves` | `MoveColony` — move it to another yard | 200, the colony | 400, 401, 403, 404, 503 |

- **A new colony** (register, swarm capture, split) is `tagId` (required, ≤ 64, unique among the account's colonies
  whatever their status), `hiveNumber` (required, ≤ 64), `yardId` (required; one of the account's yards), `hiveType`
  (required, ≤ 100), `boxCount` (required, 1–30), `occurredOn` (required, `yyyy-MM-dd`) and an optional `queen`.
- **A queen** is `source` (required, ≤ 200), `markColour` (optional; `white`, `yellow`, `red`, `green` or `blue`,
  any case), `markYear` (optional, 2000–2100) and `introducedOn` (required, `yyyy-MM-dd`). A requeen's body is a
  queen: her `introducedOn` is the event's day, and the queen she replaces gets that day as `replacedOn`. It may be
  today or earlier, never later; "today" is the server's date in UTC, which is never behind Texas, so a requeen
  entered on the day is never refused. One dated before the current queen's introduction is accepted as given, with
  a warning (*Warnings*, above).
- **A merge** is `intoColonyId` (another active colony of the account) and `occurredOn`; **a move** is `yardId`
  (another of the account's yards) and `occurredOn`. Only an **active** colony is split, merged, requeened or moved;
  a merged one stays readable with its history.
- **A colony result** is `id`, `tagId`, `hiveNumber`, `yardId`, `hiveType`, `boxCount` (as recorded when the colony
  came to be), `status` (`active`, `dead-out`, `merged` or `sold`), `origin` (`registered`, `swarm-capture` or
  `split`), `parentColonyId`, `mergedIntoColonyId` and `queen` — the current one, or null: `id`, `source`,
  `markColour`, `markYear`, `introducedOn`, `replacedOn`, `replacedByQueenId`. No event sets `dead-out` or `sold`
  yet.
- **An event result** is `id`, `type` (`registered`, `swarm-capture`, `split`, `merge`, `requeen` or `move`),
  `colonyId` (the colony it happened to; a split's parent), `relatedColonyId` (a split's new colony, or the colony
  merged into), `occurredOn`, `recordedAt` (server time), `yardId` (where a new colony was placed, or a move's
  destination), `fromYardId`, `queenId` and `replacedQueenId`. A colony's history holds its own events and the split
  that created it or a merge into it, so a split and a merge appear in both colonies' histories.
- **The queen list** is newest introduction first, as recorded. After a backdated requeen the current queen can sort
  below the one she replaced, so **the current queen is the one with no `replacedOn`** (the colony's `queen`), never
  "the first item".
- **Errors** as above, plus a `400` keyed by the field at fault for a broken rule (`tagId` taken, even by a colony
  recorded at the same moment; `yardId` not the account's or already the colony's; `intoColonyId` unknown, itself or
  not active; `id` when the colony is not active; `introducedOn` later than today), and a `503` when the colony — or,
  for a merge, the colony it goes into — changed while the change was being recorded: read it again and retry.

#### Inspection endpoints

UC-1, FR-7. The same signed-in account and acting user. An inspection is recorded once: there is no update or
delete, and `PUT`, `PATCH` and `DELETE` are answered `405` (or `404` for a path naming an inspection under a colony).

| Method | Path | Operation | Success | Failures |
|---|---|---|---|---|
| POST | `/api/colonies/{id}/inspections` | `RecordInspection` — an inspection of one of the account's colonies | 201, the inspection, `Location: /api/inspections/{id}` | 400, 401, 403, 404, 503 |
| GET | `/api/colonies/{id}/inspections?limit=&cursor=` | `ListInspections` — the colony's inspections | 200, a page | 400, 401, 403, 404, 503 |
| GET | `/api/inspections/{id}` | `GetInspection` — one inspection | 200, the inspection | 401, 403, 404, 503 |

- **An inspection** is `inspectedOn` (required, `yyyy-MM-dd`, from 2000-01-01 to today in UTC — which in the Texas
  evening is already tomorrow, so that day is accepted too), `findings` (below) and `notes` (optional, ≤ 4000,
  trimmed, blank stored as null). It needs at least one finding or a note. A result is `id`, `colonyId`,
  `inspectedOn`, `recordedAt` (server time), `findings` and `notes`, never the account.
- **There is no colony-status gate**: a colony in any status can be inspected, because the inspection that finds a
  colony dead is itself an inspection, and a refused record would be lost.
- **Findings** are an object keyed by field name; leave out a field that was not looked at (`null` counts as left
  out). Each field is one of four kinds: a flag (`true`/`false`), a count (a whole number in bounds), a choice (one of
  a list, any case, stored in the list's spelling) or a list of choices (any of a list; `[]` records that none were
  seen; a repeat is stored once). An unknown name is a `400` keyed `findings.<name>`, so a typo is never dropped
  silently. The current set, a draft to confirm with the owner:

  | Field | Kind | Values |
  |---|---|---|
  | `queenSeen`, `eggsSeen` | flag | |
  | `broodFrames` | count | 0–100 |
  | `broodPattern` | choice | `solid`, `spotty`, `none` |
  | `foodStores` | choice | `none`, `low`, `adequate`, `plenty` |
  | `temperament` | choice | `calm`, `nervous`, `defensive` |
  | `diseaseSigns` | list | `deformed-wings`, `sunken-cappings`, `ropy-brood`, `mummified-brood`, `small-hive-beetle`, `wax-moth`, `varroa-seen`, `dysentery` — observations, never a diagnosis |
  | `actionsTaken` | list | `fed`, `added-box`, `removed-box`, `swapped-frames`, `equalized`, `treated`, `other` |

- **Findings come back in the catalogue's order** (the order above) on every read, however they were sent; a stored
  name the catalogue no longer holds follows, and is still returned. A client may rely on that order for display, or
  key by name.
- **The catalogue is the authority**: `InspectionFields.All` in `ApiaryCopilot.Domain` defines every field, and the
  OpenAPI description of `RecordInspection` is generated from it. To change the field set, edit that catalogue — no
  migration is needed, the findings being stored as JSON. Widening a field is always safe; removing, renaming or
  narrowing one leaves recorded findings readable but no longer accepted on a new inspection.
- **Order:** by the day inspected, newest first, then by when recorded, newest first. **Errors** as above, plus a
  `400` on `inspectedOn` outside its range and on `findings` when nothing was found or noted.

#### Media endpoints

UC-1, FR-8, D-13. The same signed-in account and acting user. The bytes never reach the API: it signs URLs for the
phone to upload to and download from the bucket directly (Interface F). A media record is attached once and never
changed; the object behind it can still be overwritten, with the same type and length, until its upload URL expires
(F.3).

| Method | Path | Operation | Success | Failures |
|---|---|---|---|---|
| POST | `/api/inspections/{id}/media/uploads` | `RequestMediaUpload` — a URL to upload one photo or video | 200, the upload | 400, 401, 403, 404, 503 |
| POST | `/api/inspections/{id}/media` | `AttachMedia` — attach an uploaded file to the inspection it was uploaded for | 201, the media, `Location: /api/media/{id}` | 400, 401, 403, 404, 503 |
| GET | `/api/inspections/{id}/media?limit=&cursor=` | `ListMedia` — the inspection's media in the order attached | 200, a page | 400, 401, 403, 404, 503 |
| GET | `/api/media/{id}` | `GetMedia` — one media item | 200, the media | 401, 403, 404, 503 |

- **An upload request** is `contentType` (required; an allowed image or video type, any case, returned lower case,
  no parameters) and `sizeBytes` (required; the exact size, from 1 to that kind's limit, `Media__MaxImageBytes` or
  `Media__MaxVideoBytes`). **The upload** returned is `objectKey`, `uploadUrl`, `method` (`PUT`), `headers`
  (`Content-Type`, to send exactly as given) and `expiresAt`. Nothing is recorded until the file is attached.
- **An attach** is `objectKey`, one the upload request returned for this inspection. **A media result** is `id`,
  `inspectionId`, `contentType` and `sizeBytes` (as the bucket stored them), `attachedAt` (server time: when it was
  attached, not when it was captured), `downloadUrl` and `downloadUrlExpiresAt` (a fresh URL on every read); never
  the account or the key.
- **Errors** as above, plus a `400` keyed `objectKey` when the key is malformed, was issued for another account or
  inspection, names nothing uploaded yet, names an object of a type or size that is not allowed, or is already
  attached; and a `503` on every media endpoint while no bucket is configured, and on an attach when the bucket does
  not answer.

#### How the family app uses it

The family app (`src/pwa/`) calls the API on its own origin, sends `X-CSRF: 1` on every write, and parses every
response against this contract (with zod, in `src/pwa/src/api/`). A `400`'s field errors are shown on their fields and
the rest above the form, `404` as not found, `503` with its message and a retry, and anything that is not a problem
response (the proxy's `502` while the server starts, or a `401`) as the server being unreachable. It has no sign-in
screen yet: a user signs in by opening `/api/auth/login` first. It reads every page of a list (`limit=100`), except a
colony's inspections, which it reads 20 at a time on request ("Show older").

It holds no copy of the inspection field catalogue: it writes each finding from its name and value
(`queenSeen: true` → "Queen seen: yes"), in the order the API sends them. **The capture screen**
(`#/colonies/{id}/inspect`) is the one place it names fields, because a form must draw them
(`src/pwa/src/capture/fields.ts`); if the catalogue renames or removes a field, that file must follow. The screen:

- records the inspection first, then each file: `RequestMediaUpload`, a `PUT` of the bytes to the URL with exactly
  the headers returned, then `AttachMedia`;
- says "Inspection saved" only when every file is attached. A file that fails can be retried with a fresh URL, or
  left; a file the API refuses (too large) is shown with the API's message and not retried;
- re-encodes each photo as a JPEG of at most 1600 px on its long edge before sending it, and refuses a video over 60
  seconds, or of unknown length (NFR-4);
- keeps the upload URL only for the one call that uses it — never in state, storage or a log (F.3);
- keeps, on the phone (`localStorage`, `apiary-keeper.capture-readings`, the newest 50), the seconds from opening
  the screen to tapping Save and to everything saved — the measure of NFR-2, a median under 60 seconds. The server is
  not told.

### D.2 Events and streaming

None.

## Interface F — the media bucket

The API issues short-lived presigned URLs; phones upload and download directly (D-13), so the bytes never cross the
API or the proxy. Used for inspection photos and short video; voice notes and database backups are planned to use the
same bucket. On Railway the bucket is private and S3-compatible, with virtual-hosted URLs by default (path-style on
older buckets), region `auto`, free egress, a public endpoint only and no lifecycle rules.

### F.1 Endpoints and credentials

The bucket's S3 endpoint (`https://t3.storageapi.dev` on Railway), its name and one key pair, set on the server as
`Media__ServiceUrl`, `Media__Bucket`, `Media__AccessKeyId` and `Media__SecretAccessKey`, only in the environment. The
key pair never leaves the server: not in the image, a log line, an error or a result. Locally and in the integration
tests the bucket is MinIO on `127.0.0.1`, reached by the server at one address (`Media__ServiceUrl`) and by the phone
at another (`Media__PublicUrl`); each URL is signed for the address the phone uses.

### F.2 Calls

| Call | By | Purpose |
|---|---|---|
| `PUT {bucket}/{key}` on a presigned URL | The phone | Upload one file |
| `GET {bucket}/{key}` on a presigned URL | The phone | Download one file |
| `HEAD {bucket}/{key}`, signed with the key pair | The server, on attach | Learn the stored content type and length |

### F.3 What a presigned URL grants

- **One method on one object, as often as the holder likes until it expires — not one use.** It is signed with AWS
  signature V4 in the query string. Changing the method, the key or any signed value makes the bucket answer
  `403 SignatureDoesNotMatch`, so a URL cannot be bent to another key. It can be replayed unchanged, though: **whoever
  holds an upload URL can `PUT` its object again — even after it is attached — and replace the bytes**, with the same
  type and length, until the URL expires. "Attached once and never changed" therefore holds for the media record, and
  for the object only once its upload URL has expired. What bounds this: a short upload lifetime, the signed type and
  length, one attach per key, and the family app dropping the URL once its upload is done.
- **Lifetime:** `Media__UploadUrlLifetime` (default 10 minutes; keep it short) and `Media__DownloadUrlLifetime`
  (default 15 minutes), each 1 second to 1 hour; after it the bucket answers `403 Request has expired`. The bucket
  checks it when a request starts, so an upload begun in time finishes.
- **An upload URL signs `Content-Type` and `Content-Length`:** the declared type (an allowed image or video type;
  never HTML, SVG, XML or any `+suffix` type, which the server refuses in its settings at startup) and the exact size.
  The bucket refuses anything else with `403`, so a file over the limit is never stored. A download URL signs the host
  only.
- **It is a bearer credential** until it expires. The server returns it only in a response body and never logs it (a
  unit test scans the diagnostic output for any URL, key or credential).

### F.4 Object keys

`accounts/{account id}/inspections/{inspection id}/{token}`: prefixed by the account (NFR-8) and the inspection the
file may be attached to, ending in 128 random bits as 32 lower-case hex characters, so a key cannot be guessed.
Nothing from the client — a file name above all — is part of a key. A key is attached only to the inspection and
account it names, and only once (a unique index).

### F.5 Errors and degradation

The server's one call, the `HEAD` on attach, has a 5-second timeout per attempt and the AWS SDK's standard retry mode:
up to two retries on transient faults, with exponential backoff and jitter, and a retry quota that stops retrying
while the bucket keeps failing. A missing object is a `400`; any other failure is a `503` to retry, logged by its
exception type only. Signing makes no call, so issuing a URL never waits on the bucket.

### F.6 Browser access (CORS) and the proxy

The phone's requests go from the app's origin to the bucket's, so the bucket must allow that origin for `PUT` and
`GET` and the `content-type` header (the upload's type is not one CORS safelists, so the browser sends a preflight
first). On Railway that is one CORS rule per bucket — the one app domain, `PUT` and `GET`, `content-type` and nothing
broader; [`DEPLOYMENT.md`](DEPLOYMENT.md) §4 gives the command. Locally MinIO cannot hold that rule; its server-wide
CORS allows `http://localhost:5080` and `http://127.0.0.1:5080` and any header, so a local upload does not test the
Railway rule. The URLs name the bucket's host, not the app's, so neither the proxy's body limit nor its
shared-password gate applies to them.

### F.7 Open

Retention is not decided: an object uploaded but never attached stays in the bucket, and Railway's buckets cannot
expire it. It never gets a download URL, so the cost is storage only — but any signed-in `owner` or `helper` (or,
before sign-in is on, anyone past the gate) can request upload URLs, each for up to `Media__MaxVideoBytes` (200 MiB by
default), so until a retention rule and a sweep of unattached objects exist this is a storage-cost risk against NFR-7.

## Interface L — Keycloak, the identity provider

Self-hosted Keycloak with its own PostgreSQL (D-19): OpenID Connect for sign-in, OAuth 2.0 access tokens for
automated clients, while a browser is authorized on the claims of its session in the API. The server's side is built
and runs against the local and test realm (`keycloak/import/`, [`DEPLOYMENT.md`](DEPLOYMENT.md) §1); no deployed
environment runs Keycloak yet.

- **Host name and issuer.** Keycloak is published on its Railway-assigned address, not a custom domain and not behind
  the proxy (D-19, D-16). `KC_HOSTNAME` is that address with `https://`, and it is the issuer the API validates; it
  must stay stable, because deleting and recreating the Keycloak service changes it, and the issuer with it.
- **Clients and flows.** The server is the confidential client `SignIn__ClientId` (`apiary-keeper-bff` locally) with
  `SignIn__ClientSecret`, asking for the `openid` scope only, its code returned in the query to `/api/auth/callback`,
  the authorization request pushed to Keycloak first (RFC 9126) when Keycloak offers it. It reads the discovery
  document from the issuer `SignIn__Authority`, or from `SignIn__MetadataAddress` when it reaches Keycloak by another
  address than the browser does (Keycloak then needs `KC_HOSTNAME` and `KC_HOSTNAME_BACKCHANNEL_DYNAMIC`, so the
  issuer stays the browser's). The ID token and a bearer access token are accepted only RS256-signed and only from the
  issuer `SignIn__Authority`, each only as its own kind; the session takes `sub`, `account_id` and the roles named
  `owner`, `helper`, `grower` or `customer` from the ID token and nothing else, a bearer token gives the same, and a
  token without a `sub` or with other than one well-formed `account_id` is refused on either path. Phase 4 assistants
  will use the client-credentials grant, one Keycloak client each with only its own scopes (FR-72); scopes are checked
  once the first such client exists.
- **Tokens and sessions.** The server keeps the **refresh token only**, server-side beside the session (protected
  before it is cached, expiring with the session), and no ID or access token. It calls Keycloak's token endpoint with
  the refresh token grant 30 seconds before the access token expires; takes the rotated refresh token; and validates
  the new ID token as at sign-in, with the same `sub`. A `4xx` (a disabled user, a spent, revoked or expired token) or
  a response without an ID token ends the session; a `5xx`, a 10-second timeout or no answer keeps it, refusing
  requests past the access token's expiry until Keycloak answers. **A refresh is never retried**: with rotation on, a
  refresh token is good once. One renewal per session at a time; concurrent requests take its result. Sign-out posts
  the refresh token to Keycloak's logout endpoint on the back channel, ending the user's Keycloak session. Only
  Keycloak's error code is ever logged, never a token. Lifetimes: an access token of about 5 minutes, a 30-minute idle
  timeout and a 12-hour maximum session, refresh-token rotation on — Keycloak realm settings and the server's
  `SignIn__Session…` settings, not constants.
- **Brokered providers.** Google only to start, for the family app and the customer website alike. A Google identity
  links only to an invited account whose email matches its provider-verified email; there is no self-registration
  through the provider. Only the provider's subject id and verified email are stored.
- **Account lifecycle.** Invitations, email verification, password reset (a 30-minute link) and MFA (the owner may
  require it, per user) are Keycloak's, its mail going through Interface G. The server never handles a password.
- **Roles and claims** (D-22). Realm roles in one realm: `owner`, `helper`, `grower` for an account's users and
  `customer` for the storefront's customer accounts. The token carries the roles as a top-level `roles` array and a
  single `account_id` claim (a user attribute, as a string), in the ID token and the access token alike; one account
  per user. An audience mapper puts `apiary-keeper-api` in the access token. A change reaches the user with their next
  access token.
- **The server's service account** (D-22). Invitations (FR-74) and, later, customer accounts (FR-38) go through the
  server, which calls Keycloak's admin interface with its own service account (`KeycloakAdmin__ClientId`, the
  client-credentials grant). Its grant (Keycloak's fine-grained admin permissions): `manage` and `map-roles` on users,
  `map-role` on `helper`, `grower` and `customer` only, and a deny on the members of the **`owners` group**. Keycloak
  refuses it `owner` by any route, reading a user or a credential, managing roles, clients or realm settings,
  impersonation, and, on an owner, disabling, editing, resetting, emailing, deleting, reading or taking it out of the
  group. **An owner holds `owner` only through the `owners` group**, never by a direct mapping, which the deny does
  not see. **Held beyond that, accepted:** the `manage` that creating needs also edits, disables, deletes and resets
  the password of any user outside the group, sends it Keycloak's action email and gives it another member role; and
  it can add or remove `helper`, `grower` or `customer` on any user, owners included. So a leaked secret could take
  over or delete any helper, grower or customer in any account (change its email, then send the reset), though never
  an owner; the secret's custody and rotation are the control. Because the account may not read roles, the server is
  configured with the three member roles' ids (`KeycloakAdmin__*RoleId`). **An `owner`** — a new apiary account — is
  created by the Keycloak administrator in the admin console, never by the server.
- **The invitation's calls.** Per invitation, with no retry (creating a user is not idempotent) and each call bounded
  at 10 seconds: a client-credentials token from the realm's token endpoint; `POST …/admin/realms/<realm>/users` with
  the address as `username` and `email`, the name as `firstName`, `enabled`, `emailVerified` false and the
  `account_id` attribute, whose `Location` ends in the new user's id (a `409` is an address already taken);
  `POST …/users/<id>/role-mappings/realm` with the role's configured id and name; and
  `PUT …/users/<id>/execute-actions-email?lifespan=<seconds>` with `["VERIFY_EMAIL","UPDATE_PASSWORD"]`. A failure after
  the user exists deletes it again (`DELETE …/users/<id>`). Only the step and an HTTP status or exception type are
  logged; never a token, the secret, an address or a name.
- **Administrators and recovery** (D-22). The owner never sees the Keycloak console. One administrator login, with MFA,
  is used day to day; the recovery path is a second, sealed break-glass administrator, also with MFA, held apart from
  the first. Every break-glass use is logged, its credentials are rotated after every use, and it is tested now and
  then.
- **Local and test.** The realm `apiary-keeper-dev` in `keycloak/import/`, with invented users and secrets only, at
  `http://127.0.0.1:8180/realms/apiary-keeper-dev` (its issuer locally); the clients and grants are listed in
  [`DEPLOYMENT.md`](DEPLOYMENT.md) §1. **Any real realm must turn the password grant off on Keycloak's built-in
  `admin-cli` client**, as the local realm does, or anyone can trade a user's password for realm-signed tokens through
  it.
- **Open.** Changes to an existing user — its role, requiring MFA for it, a helper's finer permissions, re-enabling it,
  correcting its `account_id` — which until decided only a Keycloak administrator can make; and how an `owner` created
  by the administrator fits FR-74's wording and production's bootstrap step.

## Planned interfaces

- **A — NWS weather.** Weather per yard (wind, hail, freeze, drought, rain) from `https://api.weather.gov`, feeding
  the feeding and inspection task rules (FR-65): a yard's location resolves to a forecast grid through
  `/points/{lat},{lon}`, then its forecast and active alerts. Public data; the request names the app and a contact.
- **B — Telegram.** The family group bot (FR-23–FR-27), behind one channel interface so another platform can replace
  it (D-3): mark a task done, `/photo <tag>`, a quick note. Media goes through the app's upload path, not Telegram.
  Privacy mode stays on; staging uses a separate test bot.
- **C — Square or Shopify.** Hosted checkout for the customer website — the site never handles card numbers (FR-37,
  D-7) — and sales sync (FR-34). Order status returns by signed webhook. The provider is open.
- **E — GitHub issues.** In-app bug reports and feature requests become issues labelled `bug` or `feature-request`
  and `from-app` (plus `staging` from staging) in the product's issue tracker (FR-20, D-11), through a credential that
  stays on the server.
- **G — Transactional email.** Verification, invitations and password reset, sent by Keycloak over SMTP, and pickup
  reminders from the app (FR-38). The provider is open and must offer SMTP. Locally and in the tests Keycloak's mail
  goes to Mailpit, which keeps it and delivers nothing.
- **H — QuickBooks.** An export file, not a live integration (FR-34). Format open.
- **I — Hive scales and sensors.** Only if adopted (Phase 5), normalized to one time-series schema (FR-66).
- **J — MCP server.** Read, scoped-write and propose-only tools for the assistants (FR-67, FR-72, D-12), each
  assistant its own Keycloak client with only its own scopes.
- **K — AI model provider.** Pay-per-use, provider-agnostic, a low-cost model by default, with a monthly spend cap
  enforced in the app (D-12, FR-72).

Every integration follows the same defaults: a timeout on every outbound call; retry with backoff on 5xx and timeouts
only (Keycloak's refresh token grant excepted: it is never retried); inbound webhooks verified by signature or secret
token and processed idempotently; and an outbound failure never stops a record from saving.
